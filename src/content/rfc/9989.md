**RFC 9989 is the DMARC specification.** It obsoletes [RFC 7489](/rfc/7489/),
the informational document the protocol ran on for a decade, and puts DMARC on
the IETF standards track.

If you have ever seen DMARC described as "not really a standard" — that was
accurate, and it no longer is.

## What it replaces

RFC 7489 was replaced by **three** documents, not one. That split is the most
confusing thing about the new specification and worth getting straight first:

| Document | Covers |
|---|---|
| **RFC 9989** (this one) | The core protocol — policy, alignment, record syntax |
| [**RFC 9990**](/rfc/9990/) | Aggregate reports — the XML your `rua=` address receives |
| [**RFC 9991**](/rfc/9991/) | Failure reports — the per-message detail `ruf=` requests |

It also obsoletes RFC 9091, the experimental Public Suffix Domain extension,
folding that work in as the `psd` tag.

## The tag registry, as it now stands

Three tags became **historic**. Everything else survives with its meaning intact:

| Tag | Status | |
|---|---|---|
| `v` `p` `sp` `np` `adkim` `aspf` `rua` `ruf` `fo` `psd` `t` | **active** | `np` and `t` are new |
| `pct` | **historic** | Replaced by `t` — see below |
| `rf` | **historic** | Failure report format; only one format was ever used |
| `ri` | **historic** | Aggregate report interval |

## `pct` is gone, and `t=` is what replaced it

This is the change most likely to affect a record you already have.

`pct` let you apply a policy to a percentage of mail. The RFC's own account of
why it went (Appendix A.6) is blunt: operational experience showed the tag "was
usually not accurately applied, unless the value specified was either 0 or 100",
and behaviour for everything in between "varied widely from one implementation
to another".

But `pct=0` had become genuinely useful — intermediaries treated it as a signal
to rewrite the `From:` header, which let domain owners see how much of their
mail flowed through intermediaries that *don't* rewrite. That was worth keeping,
and a tag with only two meaningful values should not be called a percentage. So:

```
t=y    request that the policy not be applied  (what pct=0 meant)
t=n    apply the policy                        (default; what pct=100 meant)
```

`t` does not affect report generation, and has no effect where the policy is
already `none`.

**If your record has `pct=100`, delete it — that was always the default.** If it
has `pct=0`, replace it with `t=y`. Anything in between never worked the way you
thought it did.

## The other changes worth knowing

**`np` — a policy for non-existent subdomains.** Alongside `sp`, you can now
reject mail claiming to come from names that have never existed, without
loosening anything applied to real subdomains.

**Policy discovery is a DNS tree walk** (§4.10), replacing the Organizational
Domain lookup built on the public suffix list. Same intent, tighter definition,
fewer cases where two receivers disagreed about which record applied.

## What did not change

Your record still lives at `_dmarc.yourdomain.com`, still starts `v=DMARC1`, and
`p=`, `rua=`, `adkim=` and `aspf=` mean exactly what they did. DMARC still
requires [SPF](/rfc/7208/) or [DKIM](/rfc/6376/) to pass **and**
[align](/glossary/dmarc-alignment/) with the `From:` domain.

Nothing here obliges you to republish. **If your record does not use `pct`, `rf`
or `ri`, it is already an RFC 9989 record.**
